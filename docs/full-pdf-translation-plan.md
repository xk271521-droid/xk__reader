# 全文 PDF 翻译开发计划

关联项目书：[全文 PDF 翻译项目书](./full-pdf-translation-project.md)

## 当前基线

- 旧全文翻译代码及前端入口均处于关闭状态。
- 旧逻辑从浏览器上传 PDF.js 文字块，再调用逐段翻译；该链路不再作为新版的输入。
- 阅读器默认使用 PDFium/WASM，必须保持不受全文翻译实现影响。

## 实施阶段

### 阶段 1：任务与产物持久化

- 为全文翻译记录增加译文 PDF 产物路径、产物哈希、生成版本/配置快照和替换状态。
- 将启动接口改为仅基于已上传的原 PDF 创建任务，不再接收浏览器端 `pages`。
- 完成产物存在时，启动接口只返回缓存；新增显式“重新翻译”接口创建下一版本。
- 删除论文时清理所有译文产物；生成失败时保留上一份有效译文。

验收：同一论文连续请求两次只产生一个任务；完成后刷新页面仍能读取同一产物。

### 阶段 2：PDFMathTranslate/BabelDOC 运行器

- 新增独立后端运行器，以受控子进程或隔离服务调用 PDFMathTranslate/BabelDOC。
- 使用临时工作目录，验证退出状态、输出文件存在性和 PDF 文件头，再原子移动至持久化目录。
- 将主引擎、目标语言、翻译服务、术语库版本写入生成快照。
- 配置缺失时返回可操作的错误，不回退到旧的浏览器逐段翻译。
- 统一使用 SiliconFlow 的四模型候选链：`THUDM/GLM-4-9B-0414`、`Qwen/Qwen3-8B`、`THUDM/GLM-Z1-9B-0414`、`tencent/Hunyuan-MT-7B`。
- 一篇论文启动时固定一个候选模型；只在价格状态不允许、鉴权失败、限流、连续超时、模型下线或输出质检失败时，切到下一个候选。已成功段落/已保存译文不得重新发送。
- 价格状态未知时默认拒绝调用，禁止为了兜底而静默产生付费请求。

验收：给定真实论文，运行器只接受原 PDF 并保存一份可打开的译文 PDF。

### 阶段 3：复杂文档回退与阅读入口

- 当 PDFMathTranslate 报告解析失败或质量检查失败时，使用 MinerU 作为结构化解析回退。
- 前端以原文 PDF/译文 PDF 双屏关联方式打开保存产物；不改动原文批注坐标。
- “重新翻译”明确提示会创建新版本，并在新版本成功前继续保留旧版本。

验收：双栏、公式和表格论文能够打开译文 PDF；重译失败后旧译文仍然可用。

### 阶段 4：真实论文回归测试与发布

- 建立最小回归集：普通双栏英文论文、公式密集论文、复杂表格论文、扫描件各至少一篇。
- 对比原 PDF 与译文 PDF 的页数、标题、公式、表格、DOI、引用编号和阅读顺序。
- 通过后开启功能开关，并重新打包桌面端。

### 阶段 5：性能与供应商兜底

- 先解决模型请求瓶颈：限制单段重试次数、优先使用非思考模式、复用 PDFMathTranslate 缓存、将并发按供应商限额配置。
- 再优化 PDF 处理瓶颈：尽量只生成阅读器需要的单语译文产物，保留原 PDF 作为左屏；接入 BabelDOC 阶段事件，显示解析、翻译、排版和保存的真实进度。
- 全文翻译和划词翻译只共用 SiliconFlow 供应商凭据，不要求该卡成为全局启用项；未配置 SiliconFlow 时，两条 SiliconFlow 翻译链路都明确提示配置要求，不得回退到全局厂商。AI 精读和边读边问继续读取全局启用厂商。两条翻译链路独立保存选项和错误状态；百度/腾讯继续保留为划词翻译的默认机器翻译选项。

## 风险与处理

| 风险 | 处理 |
| --- | --- |
| PDFMathTranslate 依赖或服务未部署 | 功能保持关闭并给出配置提示，不退回旧实现。 |
| 翻译输出文件名或目录因版本不同 | 运行器通过受控工作目录和输出发现/验证处理，不依赖浏览器端数据。 |
| 新译文失败覆盖旧译文 | 使用候选产物路径；仅在验证成功后更新当前版本指针。 |
| 扫描件/复杂版面质量差 | 明确记录失败原因并进入 MinerU 回退，而不是默默输出错乱 PDF。 |
| 翻译成本失控 | 成功产物缓存、显式重译、记录版本和任务事件。 |

- 2026-08-09：增加产物正文覆盖质检、PDFMathTranslate 的 NumPy 2 兼容启动入口，以及超时后的整棵子进程清理。质检失败不替换已保存旧译文。

- 2026-08-09：修复快照上线前创建的全文翻译任务缺少 `provider_id` 而失败的问题。运行器会惰性绑定该用户当前启用的全局厂商并持久化快照；已失败任务保持不自动重试，符合“仅用户明确重新翻译才产生新调用”的产品规则。
- 2026-08-09：针对首个 17 页双栏真实任务的速度反馈，将后续任务的 PDFMathTranslate 段落翻译并发从 1 提升到 3（保留环境变量调低能力），并移除运行器无真实阶段数据时卡在 3% 的误导性展示。后续将利用 BabelDOC 原生进度事件接入真实阶段/百分比，不用估算值替代。
- 2026-08-09：成本审计确认速读与 AI 目录必须避免重复调用。最终交互为首次使用自动生成一次并持久化：速读在首次打开论文时启动，AI 目录在首次打开目录时启动；已有成功、进行中或失败记录均直接读取本地缓存，失败仅允许用户明确重试。后端唯一约束和前端首启保护同时防止多页签/重复渲染造成重复扣费。
- 2026-08-09：将 SiliconFlow 明确隔离为翻译专用凭据。新增/编辑时不得成为全局 AI 厂商，历史误启用记录会自动归位；全文翻译与划词翻译只读取该凭据，未配置时不回退到全局 DeepSeek/GLM；AI 精读和边读边问只读取全局启用的非 SiliconFlow 厂商。

- 2026-08-09：修复速读/AI 目录因模型 JSON 外层夹带解释或输出到 `reasoning_content` 而被判空的问题；新增宽容 JSON 对象提取、失败响应片段诊断和 4 项解析回归测试。

## 剩余发布前工作

1. 在服务器创建独立 Python 3.11/3.12 的 PDFMathTranslate 环境，配置其模型服务凭据和 `PDFMATHTRANSLATE_COMMAND`。
2. 设置后端 `FULL_TRANSLATION_ENABLED=true`、前端 `VITE_FULL_TRANSLATION_ENABLED=true`，先仅在测试环境开放。
3. 以普通双栏、公式密集、表格密集、扫描件各一篇真实论文验收；记录页数、公式/图表保留、术语准确性和重译保护结果。
4. 验收通过后再随网页端重新打包桌面端；不在 Electron 壳中另写翻译逻辑。

## 2026-09-18 页面空白故障与修复

- 现象：已生成的全文译文页面只显示“原文 PDF / 中文译文 PDF”两条标签，其余区域为空白。
- 排查结论：本地 `paper_id=196` 的译文记录为 `completed`，产物 `196/translation-v1.pdf` 存在（9,429,272 字节），受鉴权文件接口返回 `200 application/pdf`；不是翻译任务或 PDF 文件丢失。
- 根因：全文翻译前端已迁移到 PDFium 双屏组件，但迁移时遗漏了 `.full-translation-pdf-split` 与 `.full-translation-pdf-pane` 的布局规则。PDFium 内部使用 `height: 100%`，上层没有弹性高度链，导致两个已成功挂载的阅读器可视高度为 0。
- 修复：新增组件专属 `FullTranslationReader.css`，为双屏容器和每个面板建立 `flex: 1`、`min-height: 0`、双列网格及阅读器弹性高度；窄屏自动改为上下两屏。未改动 PDFium 引擎、翻译服务或已保存译文。
- 防回归：`FullTranslationReader.test.mjs` 新增布局断言；前端全量测试 116/116 和生产构建通过。待重打桌面包后，在真实桌面全文译文页面确认两个 PDF 都有可见非零高度。
